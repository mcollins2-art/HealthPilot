4) FINDINGS (ISSUES / AREAS OF CONCERN)
====================================================================

[HIGH] F-001: Potential cross-tenant job metadata exposure (job status endpoint)
Risk:
- Job status fetch does not enforce tenant boundary at query time.
- Caller with valid ingestion scope can query by numeric job id; endpoint does not compare request tenant to job.TenantId.
Evidence:
- TenantId is captured when creating jobs:
  src/HealthPilot.Api/Endpoints/IngestionEndpoints.cs:241
- Status query does not filter by tenant:
  src/HealthPilot.Api/Endpoints/IngestionEndpoints.cs:323-332
- Tenant is stored in middleware context when provided:
  src/HealthPilot.Api/Middleware/ApiKeyAuthenticationMiddleware.cs:95-98
Impact:
- In multi-tenant deployments, tenant A may learn existence/state/provenance of tenant B jobs if ID is known/guessed.
Recommendation:
- Require tenant header for ingestion job operations in tenant-restricted mode.
- Filter queries by TenantId and return 404 for mismatches.

[HIGH] F-002: Replay endpoint lacks tenant authorization check
Risk:
- Replay uses sourceJob by id only and clones TenantId from source job, but does not verify caller tenant matches source job tenant.
Evidence:
- Replay fetch by id only:
  src/HealthPilot.Api/Endpoints/IngestionEndpoints.cs:340-344
- Replay job copies source tenant:
  src/HealthPilot.Api/Endpoints/IngestionEndpoints.cs:360
Impact:
- Potential cross-tenant replay triggering if ids are discoverable.
Recommendation:
- Apply same tenant filter/validation as status endpoint.

[HIGH] F-003: In-memory queue can lose queued jobs on process crash/restart
Risk:
- Queue is unbounded in-memory channel only; queued items not persisted in queue medium.
Evidence:
- Channel.CreateUnbounded<long>()
  src/HealthPilot.Api/Ingestion/IngestionJobQueue.cs:7
- Worker depends on queue dequeue loop:
  src/HealthPilot.Api/Ingestion/IngestionJobWorker.cs:18-24
Impact:
- Jobs that are persisted as status="queued" but not yet dequeued can be orphaned after restart.
Recommendation:
- Add startup recovery sweep to enqueue persisted queued jobs.
- Consider durable broker-backed queue for production.

[MEDIUM] F-004: Destructive pricing cleanup endpoint has no dry-run/preview safety
Risk:
- Cleanup endpoint immediately issues deletions by retention age.
Evidence:
- Endpoint invokes service directly:
  src/HealthPilot.Api/Endpoints/IngestionEndpoints.cs:393-400
- Service uses ExecuteDeleteAsync on negotiated and cash tables:
  src/HealthPilot.Api/Services/PricingLifecycleService.cs:12-17
Impact:
- Operator error in retentionDays can cause broad data deletion.
Recommendation:
- Add dryRun=true preview returning counts before delete.
- Add optional confirmation token or role gate.

[MEDIUM] F-005: Retry policy hardcoded at model default
Risk:
- MaxAttempts defaults to 2 in model with no clear configuration override at job creation.
Evidence:
- src/HealthPilot.Api/Models/IngestionJob.cs:17
Impact:
- Limited flexibility; may be too strict/too lenient per environment.
Recommendation:
- Make max attempts configuration-driven and persist chosen policy per job.

[MEDIUM] F-006: Retention cleanup side effect in checkpoint list operation
Risk:
- Listing checkpoints triggers deletion of expired checkpoints as side effect.
Evidence:
- ListRecentAsync() calls CleanupExpiredAsync() first:
  src/HealthPilot.Api/Ingestion/DbIngestionCheckpointService.cs:53-61
Impact:
- Read call modifies state unexpectedly; can surprise operators and complicate auditability.
Recommendation:
- Move cleanup to explicit endpoint and/or scheduled background maintenance.
- Keep list endpoint read-only.

[MEDIUM] F-007: Error detail persistence may truncate diagnostically useful context
Risk:
- Worker stores only ex.Message to job.ErrorMessage; stack/inner details not persisted.
Evidence:
- src/HealthPilot.Api/Ingestion/IngestionJobWorker.cs:83-84
Impact:
- Harder postmortem in environments where full logs are not retained.
Recommendation:
- Persist bounded structured error code/category + correlation id.

[LOW] F-008: Queue depth/worker lag observability not exposed
Risk:
- Counters exist for completed/dead-letter events, but no queue depth/age metric surfaced.
Evidence:
- Counters only:
  src/HealthPilot.Api/Ingestion/IngestionJobWorker.cs:12-15
Impact:
- Difficult to detect ingestion backlog and SLO drift early.
Recommendation:
- Add gauge/histograms: queue length, dequeue latency, processing duration.

[LOW] F-009: Legacy API key grants broad scopes by default
Risk:
- Legacy single key path grants both estimate and ingestion write scopes.
Evidence:
- src/HealthPilot.Api/Middleware/ApiKeyAuthenticationMiddleware.cs:105-113
Impact:
- Over-privilege if legacy key mode used in production.
Recommendation:
- Encourage scoped keys only in production; optionally disable legacy mode via config.

[LOW] F-010: API docs/runbook lack explicit operational playbooks for dead-letter handling
Risk:
- Operational docs do not define dead-letter triage/replay workflows.
Evidence:
- RUNBOOK.md reviewed; no dead-letter playbook section.
- API doc lists replay endpoint but no incident flow:
  API_DOCUMENTATION.md:181-191
Impact:
- Slower MTTR during ingestion failures.
Recommendation:
- Add runbook section for queued->dead_lettered lifecycle and replay strategy.
